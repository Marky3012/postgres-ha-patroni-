A PostgreSQL cluster that fails over on its own — and proves it, on a schedule.

Two small tools, one job each: pg-ha-setup stands up a Patroni-managed, etcd-quorum-backed Postgres cluster from a single script. ha-validate then runs real failovers, real crashes, and real disaster-recovery drills against it and scores whether it's actually ready.

Why this exists

The problems a hand-rolled HA setup usually hits

Patroni + etcd solve automatic failover. They don't solve the surrounding operational gaps — the ones that only show up during an actual incident.

🌓

Split-brain risk

An even number of voting nodes can split evenly during a network partition, leaving no side with a majority to safely promote a leader.

🎛️

Manual, error-prone bootstrap

etcd, Patroni, HAProxy, and keepalived each need consistent config across every node — one typo'd peer list and quorum never forms.

❓

Untested failover

A cluster that has never actually been crashed on purpose is a cluster whose failover behavior is a guess, not a fact.

🕵️

No readiness signal

"It's probably fine" isn't a number you can put in a change-management ticket or an SLA review.

👀

Watcher node confusion

etcd-only quorum nodes are easy to misconfigure or lose track of — replacing one by hand (editing files, restarting) silently corrupts quorum.

📉

Data loss going unnoticed

A failover can "succeed" while quietly losing the last few transactions — without an explicit integrity check, nobody would know.

Two tools, one pipeline

pg-ha-setup deploys it. ha-validate proves it.

Independent projects, meant to be run back to back against the same cluster.

pg-ha-setup/

Stand up the cluster

An interactive bash orchestrator that SSHes into every target node and drives the full install: etcd quorum, Patroni-managed Postgres, optional HAProxy + keepalived VIP.

  • deploy.sh — full interactive bootstrap
  • manage-watcher.sh — safe watcher replacement
  • test-failover-failback.sh — quick manual smoke test
ha-validate/

Prove it survives a real incident

A Python campaign runner that connects to the live cluster over SSH and Postgres, runs real (not simulated) failovers and crashes, and scores overall readiness.

  • Connectivity, security, replication, performance
  • Planned switchover + failback + data-integrity checks
  • Unplanned crash + disaster recovery (gated, opt-in)
  • JSON / HTML / Excel / PDF reports with an HA-readiness score

Cluster shape

What deploy.sh actually builds

Client traffic flows through a floating VIP to whichever node Patroni has elected leader. Every node — including the etcd-only watcher — is a voter in the same quorum that decides who gets to be leader.

pg-ha-setup

One script, run once, from your workstation

deploy.sh is entirely interactive — no pre-written inventory file required — and installs/starts everything in the right order.

1

Ask & check

Node IPs, SSH key, passwords. Verifies SSH + passwordless sudo on every node before touching anything.

2

Install (parallel)

Pushes and runs remote-install.sh on all nodes concurrently — PostgreSQL 17, Patroni, etcd.

3

etcd quorum up

Starts etcd on every node simultaneously (sequential start would deadlock on quorum) and waits for health.

4

Patroni bootstrap

Leader initializes first, replicas join and stream. Self-heals stale data dirs from prior failed attempts.

5

Optional VIP

HAProxy + keepalived deployed to all PG nodes if you opted in, giving one floating connection endpoint.

# run from a control machine with SSH access to every target node
./pg-ha-setup/deploy.sh

# quick manual failover/failback smoke test afterwards
./pg-ha-setup/test-failover-failback.sh

# replace or relocate the watcher node later, safely
sudo ./pg-ha-setup/manage-watcher.sh

ha-validate

A cluster isn't "HA" until something has actually killed it

ha_validate.py runs a campaign of real checks over SSH and direct Postgres/HTTP connections — nothing is simulated locally — then scores the result. 

# non-destructive baseline — safe against production
python ha_validate.py --config config.yaml --tests safe

# everything, including a real crash + simulated site loss —
# only with a confirmed maintenance window
python ha_validate.py --config config.yaml --tests all --confirm-destructive

Two flavors

master vs. development

master is the straightforward, fixed-topology reference build. development generalizes pg-ha-setup to any node count and reasons about quorum with you as you go.

🌿 master — fixed 4+1

  • 4 PG nodes + 1 watcher, always
  • deploy.sh asks for exactly those 5 IPs
  • Simplest path to a known-good reference cluster

🚀 development — scalable N+M

  • Any number of PG nodes (2–20), watcher count computed for you
  • Watcher(s) only requested when the PG count is even — just enough added to make the etcd/DCS quorum odd again
  • deploy.sh explains the quorum math at each prompt instead of assuming a fixed shape
  • manage-watcher.sh handles multi-watcher topologies
